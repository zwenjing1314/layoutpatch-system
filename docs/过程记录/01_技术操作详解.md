## 使用与续写规则

- 每轮一个日期标题，轮次连续编号为 R01、R02……；同一天多轮分别记录，不虚构具体时刻。
- 每步编号为 `R01-S01`，一个步骤只讲一件主要事情。先看结果，再看操作与技术说明。
- 状态固定为：**已核查 / 已修改 / 已验证 / 设计完成·未实现 / 阻塞 / 未执行**。设计和运行分开写。
- 命令记录工作目录、关键参数、实际结果；长输出链接到证据，不全部粘贴。未保留原脚本的调用摘录必须注明，不能包装成可直接运行的完整脚本。
- 每轮结束同步更新两份文件及目录索引。后续记录追加在“续写模板”之前；结论改变时新增更正记录，并引用原步骤，保留历史。
- 原始设计以 requirements、architecture、interfaces 为准；本文件解释操作过程，避免维护另一套相互冲突的设计。

### R01-S02｜核实源码版本与已有修改〔已核查〕

- **为什么：**同一个提交号下，也可能存在尚未提交的本地修改。
- **操作：**对三个源库分别执行下表命令，并用 SHA256 记录已列出的改动文件内容。后续 Git 状态检查设置 `GIT_OPTIONAL_LOCKS=0`，避免可选的索引刷新写入。

| 关键命令形式 | 含义 | 实际发现 |
|---|---|---|
| `git -C <源库> rev-parse HEAD` | 查当前提交身份 | 原库`5dd4e5c…`；Snappy`acde4a1…`；精简库`4a2c006…` |
| `git -C <源库> status --short --untracked-files=all` | 查已修改及未跟踪文件 | 原库`.gitignore`已修改；Snappy Dockerfile已修改；精简库干净 |
| `git -C <源库> diff --stat` | 看已跟踪文件变化概况 | 保留已有差异，未覆盖或提交 |

`<源库>`表示三个实际目录，完整路径与清单见 [源状态快照](../checks/source-state-before.json)。`HEAD`回答“基于哪个版本”，SHA256回答“文件内容是否一致”；二者都不证明程序能运行。此步没有修改源码。

### R01-S06｜读懂页面检索与区域排序接口〔已核查〕

阅读 `colpali_layout.py`、`route_v2_layout.py`、`route_v2_attribution.py`、`route_v2_scoring.py`、query缓存和布局/融合模块，确认以下接口约束：

| 输入或规则 | 技术含义 | 对接时要保留什么 |
|---|---|---|
| 页面`[1031,128]` | 1031个token，每个128维 | 前1024行是32×32视觉patch，后7行是prompt |
| 问题`[T,128]` | T个有效问题token | 按attention_mask去补齐，保留真实增广token |

### R01-S07｜核对权重身份并做有限加载检查〔已验证〕

- **操作：**从冻结 weights.json 找到三份 D-no-text checkpoint；核对权重、清单、训练配置和选择记录的 SHA256；在 CPU 上严格加载。另比对原库与精简库的7个核心源码文件。
- **关键调用摘录：**`torch.load(path, weights_only=True, map_location="cpu")` 后调用 `InputAblatedD("text").load_state_dict(payload["state_dict"], strict=True)`。这是操作摘要，变量省略，非完整运行脚本。
- **参数解释：**checkpoint保存已训练参数；`weights_only=True`限制反序列化范围；`map_location="cpu"`指定加载设备；`strict=True`要求参数名称与形状符合当前模块。
- **结果：**三份权重哈希匹配、strict load全部通过，模块273410个参数；7个核心源码文件字节一致。torch加载前的临时目录问题及进程内诊断设置见下一步。
- **边界：**只证明文件身份和结构匹配，未调用forward进行推理，未证明排序效果。未重训、改权重或选外部成绩最好的seed。证据见 [权重核查](../source-audit.md)。

### R01-S08｜记录导入失败并缩小问题位置〔阻塞〕

| 实际操作顺序 | 结果 | 可得结论 |
|---|---|---|
| 研究Python使用`-B`导入torch | 在dill/tempfile处报无可用临时目录 | 尚不能直接复用该环境运行 |
| 试探临时文件创建 | 调用未结束，终止了该诊断进程 | 保留失败，未修复系统目录权限 |

### R01-S09｜设计登录、角色与文档隔离〔设计完成·未实现〕

将以下规则写入 [需求](../requirements.md) 和 [架构](../architecture.md)，没有新增登录路由或数据库：

| 设计决定 | 如何理解、将来怎样落实 |
|---|---|
| 一个登录入口，两种角色 | 角色由后端账号记录决定，不能由登录页面自行选择 |
| 普通用户私有库＋管理员共享库 | 上传时由服务端写owner_id；用户只能读自己的文档和共享文档 |
| 管理员跨用户管理需留痕 | 管理员不是“不受检查”，仍记录操作者、对象和时间 |
| 服务端会话＋HttpOnly Cookie | Cookie携带会话ID；服务端查会话有效性。HttpOnly限制页面脚本读取Cookie |
| 密码哈希、CSRF与撤销会话 | 哈希用于验证密码；CSRF防其他网站借登录状态发写请求；退出/停用后旧会话失效 |
| 检索前生成可访问文档版本白名单 | 数据库先确定范围，Qdrant在范围内取Top-k，不能全库取完再删除越权结果 |
| 预览/任务/历史同样授权 | 即使知道page_id/job_id或原URL，也需要重新核对归属 |

**技术理解：**认证回答“你是谁”，授权回答“你能访问什么”。401表示未认证，403表示角色权限不足；他人对象按设计统一返回404，减少暴露对象存在性。库选型和安全行为仍需后续实现与测试。

### R01-S10｜设计存储分工与任务生命周期〔设计完成·未实现〕

- **架构分工：**Next.js显示界面；FastAPI协调请求和授权；SQLite保存账号、归属、任务等业务记录；Qdrant保存页面检索向量；文件目录保存PDF、页面图及完整特征。
- **数据关系：**用户拥有文档，文档有版本，版本包含页面，页面对应解析候选；任务和检索记录绑定实际配置身份。
- **任务规则：**入库状态写入数据库；重启后未完成任务标为interrupted，并允许可追踪重试。模型执行先限单并发，避免多进程重复占显存。
- **删除规则：**先把文档标为不可访问，使检索和预览立即排除；再清理索引、文件与缓存，失败保留可重试状态。
- **技术理解：**SQLite存“谁拥有哪个文档”，Qdrant解决“哪些页面相似”，二者职责不同。持久化是状态写入存储而非只留在内存。本步只有 [架构图与实体设计](../architecture.md)，未建表、迁移或启动容器。

### R03-S05｜实现最薄编码与页面排序链路〔已修改〕

| 新文件/模块 | 具体实现与原因 |
|---|---|
| [colpali_adapter.py](../../backend/algorithms/colpali_adapter.py) | 加载/身份验证、单页编码、批量问题编码，保存实际forward次数和token审计 |
| [contracts.py](../../backend/algorithms/contracts.py) | 校验非空/有限/近单位长度向量；完整页必须1031×128；MaxSim与稳定Top-k |
| [verify_colpali_local.py](../../scripts/verify_colpali_local.py) | 接收问题/问题文件；核验完整PDF及页图；每次全部重编码；对照参考并保存结果/错误 |
| backend及algorithms的两个 `__init__.py` | 建立可导入的算法包；没有顺带创建HTTP业务服务 |

**两个容易讲错的细节：**页面前1024行是视觉patch，后7行是prompt，页面检索用全部1031行；问题仅删除attention_mask为0的补齐行，不能按pad token ID删除。实测每个问题都有10个pad-ID有效增广token。

**如何评分：**将编码向量转CPU float32；每个问题token在一页中取最大相似度，然后求和。13页全部评分后按分数排序，同分按page_id；k限制1—50，重复ID/非法分数报错。分数不是置信概率。

**失败处理：**输出目录必须位于runtime且尚不存在；错误写report/error.txt，不读取旧预测补位。当前仅处理显式开发语料，尚无账号、授权过滤或向量库。
